MC Training gym readiness

The app logs sets well under ordinary use: one tap accepts a fully prefilled set, an exercise can be done out of order, and a whole workout can be logged with no signal. It isn't yet dependable for the interruptions a real gym brings: a phone call, a locked screen, a peek at next week, a deploy, a borrowed bench. This page records 54 stress scenarios, each run in a real browser against the real modules.

What a lifter would notice

  • The screen locks between early sets. No wake lock is held during the first exercise, and none after a phone call.
  • Tapping a week tab erases the session. On all 7 tabbed engines, ticks, the resume banner and crash recovery go with it.
  • History shows x-incline-db-press instead of exercise names, for every real workout.
  • "Suggested: 195 lb", but one tap logs 185. The suggestion never reaches the prefill.
  • After a deploy, the program isn't offline any more, while the dashboard still says "Available offline ✓".

Decisions you made for this phase

  • Keep the screen on for the whole session, re-acquired after interruptions, with a setting to turn it off.
  • Swaps are today-only by default with an opt-in "keep", and the substitute's sets go to its own history.
  • Adopt your 48px target and 8px spacing standard, and move the CI gates from 44 to 48.
  • This PR carries all three audits and the roadmap. Fixes ship phase by phase.
  • Defaults I chose (say if you disagree): CSV export, merge-safe import with confirmation, a backup nudge plus share-sheet save for signed-out users, and an optional IndexedDB crash journal.

Root cause
mc-session.js wires its re-render guard (DEF-CR-02) only inside if (session) { … }, meaning only when a record already existed at page load. A workout started fresh on that load has no guard. The week change re-renders the cards without ticks, save() captures zero ticks, and it runs delete s0[PID]. The sets survive in mc_setlog_v1, so they still bank on Finish, but with setsChecked: 0.

A refresh mid-rest loses the timer, and a refresh mid-typing loses the number

FailDriven + root-caused
Rest timer
The stored timer reads null the instant a rest starts. wrapTimers() records the timer and then calls the original TMR.start(), which begins with this.stop(). That is the wrapped stop, so it nulls the record it was just given. The file header promises "a still-running rest timer (re-armed from its wall-clock end time)". Even if the record survived, the restore path (TMR.setTime) only updates the floating timer, and set-log pages hide that float in favor of the inline row.
Typed weight
A weight typed but not yet ticked is saved to mc_setlog_pending_v1 only on blur. I typed 142.5, waited, and reloaded with the field still focused. The pending store was {}, and the field came back empty.
What works
Ticked sets, the open exercise, the 5/46 counter and the elapsed clock all came back after a refresh. A deploy that lands mid-workout is held until no set is ticked.

Root cause
Three gaps stack up. The session lock starts in mc-summary.js's startTimer(), which runs only once exDone > 0, meaning a whole exercise is finished. The per-rest lock in mc-live-tracker.js only re-checks when #timerFloat's class changes, and the inline rest row means that float never changes on set-log pages. onShow() re-acquires only while a rest is running, so a session lock lost to an interruption stays lost. mc-interval.js already re-acquires on every return, so the fix has a model in the tree.
Rest-end cue
It fires exactly once when the page returns (vibrate plus three tones), with no double alert. Nothing fires while the phone is locked, and there's no notification fallback. On iPhone, navigator.vibrate is a no-op, and the Web Audio beep is likely muted by the silent switch. That last point needs a real device to confirm.

Root cause
sw.js's activate deletes every cache except the new CACHE_NAME, and each deploy bumps that name (currently v183). Only dashboard.html and index.html are precached. mc-offline-prefetch.js records "done" per program for 14 days, with no tie to the cache version, so ensure() declines to refetch. The dashboard paints the stale record as "Available offline ✓".
Also
Logging and finishing a whole workout offline works (2 sets saved). Per-set cloud inserts made offline are dropped rather than retried. The store-level sync catches up, but PR baselines and crash recovery read the per-set table. Offline, the updater's rejected reg.update() calls logged 6 unhandled errors into a 20-entry error buffer.

Data mobility & history

Can an athlete lose their history?

Backup & restore

  • Round trip exact. Export → wipe → import restored every exported store byte for byte (verified on a 4-store backup).
  • Older backup erases newer work. Restoring a 3-workout backup on a device holding 4 left 3, with no confirmation. importJSON() replaces each store wholesale.
  • JSON only. There's no CSV for a spreadsheet or another app.
  • Hard to find. Export sits below the fold of the avatar sheet, under a "Sign in" heading. Signed-out athletes see no backup status and get no reminder.

History integrity

  • Names. Finished sets store the history key, so every real workout reads x-incline-db-press in History and Detail. The committed tests seed readable names, which is why no gate sees it.
  • Collisions. Keys are truncated to 24 characters, so 34 catalog exercises share 12 keys. A Slight Incline Dumbbell Fly shares history with the Press.
  • Muscle drift. Classifying the stored key instead of the name moves 187 of 580 exercises. Barbell Deadlift reads as legs, and Face Pulls drop to "other".
  • Retention. 200 workouts (the cloud is trimmed too) and 5 sessions per exercise.
Storage is not the constraint. At the caps, training data is about 750 KB (about 1.5 MB counted as UTF-16) of a ~5 MB per-origin budget. That budget is shared with Mike's Cookbook, which runs on the same origin; its share wasn't measured. The real exposure is a signed-out athlete with one device. Invite-only accounts mean that's most athletes, and their only copy is local. Safari may also evict a browser-tab install's storage after 7 days without use; that's WebKit's published policy as I understand it, not verified here.

Flagship polish action plan

From functional to five stars

Ordered by what costs an athlete the most. Each phase opens with an AskUserQuestion check-in, per CLAUDE.md's multi-phase rule; this page serves as its discovery artifact. Each phase notes which Phase 2 roadmap phase it overlaps (A–J). Every step lists the gate that proves it, written so the gate fails on today's code first.

R1Never lose a set or a tickOverlaps A · session continuity & capture›
  1. Guard every re-render. Subscribe the re-restore to MC_SCAN whether or not a record existed at load, and never delete a record while today's mc_setlog_v1 holds sets for this page.
  2. Persist the rest timer. Record the timer after the original start() runs. On restore, mount the inline row, not just the float.
  3. Keep what was typed. Save the pending value on input (debounced), and flush on visibilitychange and pagehide.
  4. Untick means delete. Remove the set from the local store as well as the cloud, so Finish saves only ticked sets.
  5. Phase 2 carry-overs: the custom-workout Finish (A2), deletion records (A3) and merge-safe import (A4).
  6. Optional crash journal. An IndexedDB write with durability:'strict' per set closes the ~2 s window for signed-out athletes. Verify on iOS first.

Method & limits

How this was tested

Run in this audit

  • A real sw.js on a mirror of the production origin: a local HTTPS copy served as mcross2298.github.io through Chromium's host resolver. It covered install, prefetch, going offline, logging and finishing a workout, and a simulated deploy (cache v183 → v184).
  • Hard kills: SIGKILL to every process on a persistent profile at 7 delays after a tick, then relaunch and read storage.
  • Backgrounding: a simulated hidden/visible cycle with a 150-second clock jump, with recording stubs for wake lock, vibration and audio tones.
  • Week-tab round trips on 7 engines; mid-exercise swaps, reorders and out-of-order logging; seeded prefill histories; export → wipe → import through the real account sheet.
  • Measured target size, spacing, thumb position and text size at 390×844, and classifier drift over all 580 catalog names using the logger's exact key rule.

Not verified here

  • iOS behavior: the silent switch, audio while music plays, background suspension timing, and WebKit's storage flush and eviction.
  • Real network conditions. Offline was a stopped server plus browser offline mode.
  • Simulated backgrounding doesn't suspend timers the way a phone does. The end cue fired while "hidden" here; on a phone it fires on return.
  • Kill timing is one trial per delay on one Chromium build.
  • Live sign-in and the Supabase round trip were blocked in browser runs.
  • Mike's Cookbook's share of the shared storage budget.
