5 Whys — root cause analysis

DEF-CR-01
  1. A completed set redisplayed the prescribed reps, not the performed reps, after a mid-session reload.
  2. Because the row's inputs still held what build() put there — the prescription, styled as a ghost suggestion.
  3. Because the local reload path never repainted the inputs; it only added the tick class and text.
  4. Because there were TWO restore implementations and only the cloud one repainted values, cleared the ghost and set aria-checked.
  5. Because nothing required them to be one implementation. check-single-impl.js guards exactly this class of drift for makeRestTimer and applyReplacements — restore was never added to its list.
DEF-CR-02
  1. A mid-session reload left the page reading as untouched, with the session record gone.
  2. Because save() deleted the record, having read a tick-free DOM as 'nothing in progress'.
  3. Because the DOM was genuinely tick-free at that moment — the engine had just rebuilt its day cards.
  4. Because restoreSets() had already painted the OLD cards and latched as done, so nothing re-applied it to the new ones.
  5. Because restore was modelled as a one-shot at init, while this engine's DOM has more than one generation per page load.
DEF-FIN-01
  1. Restoring a legitimate backup left the app unable to render.
  2. Because readers indexed data.house, data.closes and others that the payload did not carry.
  3. Because migrate() never created them for that payload.
  4. Because those backfills sit inside version-GATED steps, and the payload claimed a version at or above the gate.
  5. Because 'claims a version' was treated as 'has that version's shape'. migrate()'s own header identifies this exact trap and defends against it — for six keys, chosen one at a time as each was met, rather than as a class.
DEF-CB-01 / CB-02
  1. Eighteen recipes carry nutrition or scaling figures that contradict themselves.
  2. Because the calorie figure and the macro figures, and the two serving tiers, were authored from different sources.
  3. Because nothing compared them after authoring.
  4. Because validate-recipes.js checked structure — fields present, ids unique, every recipe reachable — but never arithmetic.
  5. Because 'valid' had been defined as well-formed rather than self-consistent. A record can satisfy every structural rule and still tell the cook two different things.
DEF-08
  1. The weekly check-in has never reached a trainee.
  2. Because all 10 scheduled runs failed, every one in 5–8 seconds.
  3. Because the workflow exits at its own guard when WEEKLY_CHECKIN_SECRET is unset.
  4. Because the secret was never set after the workflow merged.
  5. Because the workflow shipped and its two manual configuration steps did not — and nothing failed loudly enough on a Sunday to prompt anyone. A scheduled job that fails quietly is indistinguishable from one that never ran.
The pattern across all five. Four of the five bottom out in the same place: a rule that was applied to the instances someone happened to meet, rather than to the class. One repaint implementation existed and a second grew beside it. Six keys were defended and the seventh was not. Structure was validated and arithmetic was not. Each fix in this run therefore closes the class — a single repaint both paths call, an unconditional belt rather than another gated key, a checker that compares numbers rather than another named field.
